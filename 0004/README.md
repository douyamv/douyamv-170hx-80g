# 0004 — 折叠消除（pre-bootstrap 时序）

## 解决什么错误

**折叠（别名/回卷）**：对 >40G 地址写入，数据落到内存开头——高区块"存着"低区块
的数据。稀疏写完全测不出来；整块写满+全量回读会看到大面积坏字。

## 方法

寄存器组合与 0002 相同（CFG1=0x02779000 + LMR=0x28B + SS/CSTATUS），
**差别只有一个：执行时机必须在 GFW（GSP 固件引导）做 HBM 训练之前**。

- 训练**前**写入 → GFW 按 20 FBPA × 4GiB 全几何建训练表 → 高区真解码；
- 训练**后**再改 → 训练表已按 40G 建好 → 寄存器开了也没用，高区继续回卷。

这就是 pre-bootstrap 架构：HS fire 挂在开机早期（gate 管时序），驱动起来时
几何已经是 80G。

## 验证（必须两件都做）

1. `aliasmap.cu`（本目录）— 别名距离测量：折叠时高区块回报低区块数据；
2. `vmmfull.cu <GB>`（本目录）— **整块写满 + 全量回读**，输出
   `VERIFY done checked=N bad=0` 才算过。
   ⚠️ 稀疏写（每块几十字节）测不出折叠，历史上多份"无折叠"结论就是这么误来的。
   每个 `cudaDeviceSynchronize()` 必须查返回值，否则拿到假 `0 bad`。

## 依赖

- **0001**（通道）+ **0002**（寄存器组合）。

## 坑

- 本编号只解决"地址译码几何"层面的折叠。**下游 HBM 行寻址仍有独立上限**，
  >40G 数据正确性见 0013（未解决），别把这两个混为一谈。

## 支撑文件

- `aliasmap.cu` — 别名距离测量
- `vmmfull.cu` — 整块写满+全量回读（用法 `./vmmfull <GB>`）


## ⚠️ 2026-09-02 重大修正（用户批准）：只解决了寄存器/几何层

实测真相（vmmchunk 分块整块写满+全量回读，目标机B，fire 全开当次 boot）：

- **寄存器层折叠 = 已解决且持续有效**：当场 cstatus 验证 20×FBPA 全 0x1000(4096MiB)
  =81920MiB，CFG1=0x02779000 全对。
- **物理数据层折叠 = 从未消除**：模 38.75G 绕回。39G 恰坏 0.25G、45G 恰坏 6.25G
  （写 PA X 会同时落到 X+38.75G 的单元）。
- **旧"77G 零坏"证据作废**：vmmfull 当时为抽样校验（`checked=140`，77G 只查 140 点），
  对一致性折叠是盲的。凡 `checked=N`(N很小) 的通过记录一律不可信。
- **唯一可信工具**：`vmmchunk.cu`（本目录）——每块 256MB 整块写满 + 全量回读 + 坏块图。
  判据必须看 `ALL CLEAN`，且总量≤38.75G 才可能 CLEAN。

剩余根因：HBM logic die 行寻址（Samsung 8Gb 降级），路线 = I1500 WIR 注入
（见 `../../docs/ROOT_CAUSE_and_PLAN.md` 路线A）。
